# 成果与提交标准

本文件定义第 1–32 周主线及第 33–40 周强化的通用成果标准。阶段文档决定“本周做什么”，本文件决定“什么证据才算完成”。原主线毕业与专项通过分别验收，既有门禁不被追加内容替代。

三个学习方向及项目演进见[完整路线](README.md#三个学习方向)。应用、平台与业务成果按下述门禁衔接验收，框架独立成果、平台集成成果和业务证据各自保留，不能相互替代。

## 每周完成定义

每周成果必须同时满足：

- 有可运行代码、可检查文档、固定数据或可复现实验。
- 个人学习仓库的 `deliverables/week-XX/README.md` 链接真实成果，不复制源码；课程仓库同路径只保存公共要求和空白模板。
- 记录实际运行或人工验收命令、日期和结果摘要。
- 至少保留一个失败、边界、安全或降级案例。
- 说明已经实现、尚未实现和已知限制。
- 不包含真实密钥、生产数据、客户身份信息和未脱敏日志。
- 涉及代码时记录运行时、构建工具、关键依赖版本、测试命令和实际退出状态。

只阅读文档、只保存截图、只让模型生成代码但未运行，均不算完成。

## AI 零基础认知证据

零基础改变教学顺序，不降低成果标准。新概念首次学习时，成果或周笔记必须留下：

- 学习者自己写的一句话解释，不复制百科、官方文档或模型回答。
- 一个已有开发经验类比，并指出类比不成立的边界。
- 可观察的输入、输出、实验现象或运行记录。
- 一个反例、失败、安全或“不适用”场景。
- 这个概念对当前代码、质量、成本、安全或业务流程的工程意义。

第 1–4 周的核心实验统一使用“输入 → 观察 → 解释 → 反例 → 工程意义”记录。只会执行 Quickstart 但不能解释观察和失败原因时，最多证明 L1；不能以术语卡代替运行、排错、Teach-back 和变体任务。

同一核心概念应至少在三个层次留下证据：首次建立直觉、在代码中实现或制造失败、在后续框架或平台中迁移和治理。每个新框架仍需说明它替代了哪些原生能力、增加了哪些状态和失败模式。

语言切换按[开发语言路线](01-language-roadmap.md)执行。桥接任务用于解除语法和工具链阻塞，不单独替代 AI 成果；第 5–8 周 Java 成果、第 9–13 周 Python Agent 成果和第 14 周 Java/Python 契约对照均属于必验证边界。

## 四类成果门禁

### 原理与框架成果

- 必须包含一个原生或最小实现，说明框架隐藏的行为。
- Spring AI、LangChain、LangGraph、Claude Agent SDK 均必须有独立可运行成果。
- 框架对比基于同一数据、任务和指标，不基于产品宣传。
- 版本、模型、Prompt 和参数有记录。
- 跨语言迁移使用相同任务、输入、模型条件和评测口径，并说明语言/框架新增的状态与失败模式。

### 平台能力成果

- 有 API/Schema、状态模型、权限模型、代码、测试和运行证据。
- 配置、Agent、Workflow、Tool、Prompt、KB 索引必须版本化。
- 控制面和执行面职责清晰，运行绑定不可变发布快照。
- 至少覆盖成功、校验失败、越权、依赖失败和恢复/回滚。
- 有 Trace、延迟、Token、成本和错误分类。

### 业务落地成果

- 目标、Owner、用户和业务指标明确。
- 同时包含 AS-IS 主流程、异常流程、根因和 TO-BE 流程。
- 结论区分事实、假设和建议；关键假设有验证计划。
- 包含数据、接口、权限、人工兜底、试点、回退和运维设计。
- 最终结论基于 Baseline 与试点数据，允许得出停止或调整结论。

### 生产交付成果

- 干净环境可以按文档启动。
- 固定测试集、Eval、安全攻击集和压测可以重复执行。
- 关键告警有 Runbook；备份、恢复和版本回滚实际演练。
- 发布门禁覆盖功能、质量、安全、成本和业务指标。
- 已知限制、适用边界和残余风险公开记录。

## 杭州岗位能力证据（2026-10-22 修订）

这些证据细化现有门禁，不额外要求一套作品；岗位来源、优先级及时间替换见[杭州招聘与课程对齐](10-job-market-alignment.md)。全部实际材料仍写入个人仓库。已通过记录不静默撤销，缺项由下次 REVIEW 记录补证与后续影响。

- 第 3 周：同一小改动有任务约束、AI 建议、人工修正、测试、实际耗时和模板变体；不能凭一次实验声称普遍提效。
- 第 8 周：上下文构造有预算测试，保留关键约束与完整工具消息配对；必要信息放不下时明确失败。
- 第 10/20 周：先完成纯向量与混合检索对照，再完成混合检索有/无重排对照；固定模型、数据、Chunk、TopK 和评分。必须记录失败、延迟与 ACL，无提升也可凭有效实验和诊断通过。
- 第 15 周：20 条 RAG 和 10 条 Agent 按开发 15+7、留出 5+3 固定划分；逐层评分、五条人工复核和分歧处理可追溯。模型裁判不能代替权限/副作用断言，留出集不能反复用于逐题调参；小样本不证明生产质量。
- 第 15 周失败复现：选已有一例绑定 Case/Run/Trace 与版本，提供最小脱敏输入、命令、预期/实际和失败定位；确定性 Fake 回放与真实模型重跑分开，不重放真实写入。
- 第 19 周：基准记录硬件、并发、长度、模型/量化版本、首 Token 延迟、总延迟、质量和成本口径；不能把本地硬件算零成本或把 Stub 性能当真实推理性能。
- 第 20 周：会话状态、跨会话记忆与审计边界清楚，Project/session 隔离、历史清理和上下文预算经过测试。
- 第 22 周：持久 Checkpoint 经进程退出/重启验证；外部持久 Stub 写成功但回执丢失、本地成功 Checkpoint 前退出时，按同一幂等键核对外部凭证，恢复后副作用计数为 1。保留复现命令与 Run/Step/Trace，无法确认结果时待核对，不能假成功或盲写；恢复不扩大原授权。
- 第 24 周：CI 实际执行固定回归，记录基线通过、劣化失败、退出状态和报告；无真实服务时明确未验证真实质量/延迟/成本门禁。
- 第 25/30 周：场景有杭州目标岗位的业务关联和可得的 Owner/授权数据；至少一条试点或模拟反馈经脱敏、人工审核进入数据集新版本，关联 Case ID 与回归结果，保留原基线。
- 第 30 周指标：同一入组任务集合、窗口和版本下，区分自主完成、人工接管后完成、失败、超时、拒绝与未完成，状态互斥且总数可核对；人工介入事件另记。明确完成率分母和单位完成成本公式，包含失败/重试开销、单列人工成本，零分母记 N/A，真实与模拟分开。
- 第 32 周：在最终报告附两份杭州目标岗位 JD 的链接、核验日、地点/职级、职责/必需/加分项及证据映射，写三条可核实项目描述；每条有事实、版本、指标条件、个人贡献、AI 辅助范围及限制，至少一条链接第 15/22 周失败复现命令，现场独立完成一个变体。

## 阶段出口规则

阶段出口只能使用“通过”或“未通过”。任何核心验收缺少运行证据时均为未通过。若外部 API、真实业务系统或生产环境不可用：

1. 使用 Fake、Stub 或沙箱完成本地闭环。
2. 明确哪些接口或指标尚未在真实环境验证。
3. 不以模拟结果冒充真实业务收益或生产验证。

## Commit 建议

使用 Conventional Commits，例如：

```text
feat: add versioned agent registry
test: add workflow recovery scenarios
docs: document as-is and to-be business process
chore: add production readiness checklist
```

一个 Commit 只表达一个主要意图。课程仓库和个人学习仓库分别提交；个人仓库每周可以有多个小 Commit，周末成果 README 负责汇总，不要求为了形式强行压成一个提交。
