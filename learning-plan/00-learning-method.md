# 学习方法与建议

## 每天 1 小时的固定节奏

| 时间 | 动作 | 要求 |
| --- | --- | --- |
| 10 分钟 | 复习 | 回顾昨天的代码、问题和未完成项 |
| 20 分钟 | 学习 | 优先看官方 Quickstart 和当天相关章节 |
| 25 分钟 | 实践 | 写代码、运行测试或形成可检查文档 |
| 5 分钟 | 复盘 | 记录结果、问题和下一步 |

如果当天只有 30 分钟，优先保留实践和复盘；如果有 90 分钟，多出的时间用来补测试，不要提前堆积新知识。

## 当周语言与切换方法

每天开始前先从[开发语言路线](01-language-roadmap.md)确认当周默认语言。第 1–4 周默认用 Python 观察 AI 原理与原生协议，第 5–8 周切换到 Java/Spring AI，第 9–13 周使用 Python Agent 生态，第 14 周起组合 Java 控制面与 Python 执行面；TypeScript 只在管理流程需要界面时按需补充。

语言切换日仍只学习一个 AI 核心概念。若语法或工具链不熟，先用 15–30 分钟完成阶段文档中的桥接任务，并把当天 AI 目标缩小为一个可运行输入输出和一个失败案例。不要用完整语言教程挤占 AI 主线，也不要因为熟悉另一门语言而替代必须使用 Java 或 Python 的框架成果。

每次代码练习同时记录运行时/依赖版本、测试命令和退出状态。框架代码能运行但无法说明它替代了哪些原生代码、状态在哪里、失败如何暴露时，仍只算 L1。

## AI 零基础每日闭环

每天最多引入一个核心新概念。学习顺序固定为：

```text
开发经验类比
→ 一句话定义和最小术语集
→ 可观察的最小实验
→ 一个反例、失败或安全边界
→ Teach-back
→ 改变输入或约束的小型变体
```

例如第一次学习 Tool Calling，可以先把它类比为“模型生成一份待执行的函数调用请求”，再观察工具名、参数和 call ID，最后用未知工具或非法参数证明模型请求不等于应用已经授权执行。不要在同一天继续堆叠 Agent、MCP 和工作流。

只会照着 Quickstart 运行属于 L1。能够用自己的语言解释输入、输出、观察结果、失败原因和工程意义，才进入 L2；独立实现和排错要求仍按阶段出口执行。

## 术语与心智模型记录

第一次遇到新术语时，只记录完成当前任务所需的最小内容：

```text
术语：
一句话解释：
开发经验类比：
不是什么：
可观察证据：
待验证问题：
```

- 定义必须用自己的语言，不复制百科或模型回答。
- 类比只用于入门，后续实验发现不一致时要修正，不能把类比当完整原理。
- “可观察证据”必须来自代码、请求响应、Trace、指标、实验或失败结果。
- 同一概念要在首次理解、代码实现和后续框架/平台迁移中至少接触三次。

## 零基础卡点分类

| 卡点 | 识别表现 | 处理方式 |
| --- | --- | --- |
| 第一次接触尚未记住 | 能重新理解，但术语混淆 | 使用术语卡并在次日、周日和下一阶段间隔复习 |
| 错误心智模型 | 能复述，但预测实验结果错误 | 设计最小反例，先观察现象再修正解释 |
| 语言或框架阻塞 | 理解目标，但不会使用必要语法或工具 | 安排 15–30 分钟桥接任务，只补当前任务所需内容 |
| 缺少运行证据 | 能描述方案，但没有亲自运行 | 回到最小示例，保存命令、输入、输出和失败记录 |

补救可以延迟计划，但不能通过跳过失败、安全、测试或框架内容维持表面进度。

## 每周节奏

| 时间 | 重点 |
| --- | --- |
| 周一 | 明确本周目标，完成最小初始化 |
| 周二至周四 | 学习核心概念并完成最小实现 |
| 周五 | 补异常、边界和安全控制 |
| 周六 | 测试、对比和整理代码 |
| 周日 | 完成周成果、验收、复盘并提交 Git |

周日原则上不引入大块新内容。如果成果无法运行或没有验证证据，优先补齐闭环。

## 32 周的双线学习法

前 16 周以原理和框架能力为主，后 16 周必须同时维护平台工程线和业务落地线：

- 平台工程线每天都要留下代码、Schema、测试、Trace、指标或运行证据之一。
- 业务落地线每天都要留下访谈、流程、数据口径、决策、评审或试点证据之一。
- 技术能力不能替代业务价值证明，业务反馈也不能替代工程质量门禁。
- 如果没有真实业务对象，可使用高保真案例，但必须明确角色假设、数据来源和未验证项，不得把模拟指标写成真实收益。

进入第 25 周后，每天 1 小时建议拆成 10 分钟整理证据、20 分钟调研或设计、25 分钟实现或验证、5 分钟写决策记录。涉及访谈、评审或联调时，可以把多天时间合并为一次较长活动，但当周总投入和成果标准不降低。

## 高效学习建议

### 1. 围绕问题学习，不要通读框架

当天要做结构化输出，就只看模型、Pydantic 和输出相关文档；当天要做审批，再看 LangGraph interrupt 或 Claude 权限。框架文档变化快，按任务检索比从头通读更有效。

### 2. 每个概念都完成最小闭环

例如学习 RAG 时，闭环必须包含：

```text
准备资料 → 切片 → 建索引 → 检索 → 回答 → 引用 → 失败案例
```

只成功调用 Embedding API 不算完成 RAG。

### 3. 一次只改变一个主要变量

优化 RAG 时，不要同时改 Chunk、Embedding、TopK、Prompt 和模型。每次只调整一项并在固定问题集上复测，否则无法判断提升来自哪里。

### 4. 先写验收标准，再让 Agent 动手

Coding Agent 任务至少说明：

- 要解决的问题。
- 允许修改的范围。
- 明确不做什么。
- 验收命令和成功条件。
- 是否允许写文件、执行 Shell 或访问网络。

### 5. 区分事实、推断和建议

代码分析记录应标明：

- 已验证事实：有代码、日志或测试证据。
- 合理推断：根据现有信息推测但尚未验证。
- 后续建议：可以尝试但不代表已经解决。

### 6. 保留失败样例

不要只保存成功截图。至少记录一次：

- 检索没有召回正确文档。
- 模型选错工具或传错参数。
- Agent 修改后测试失败。
- 权限规则成功拦截危险行为。

失败样例是后续评测和面试表达中最有价值的材料。

### 7. 先单 Agent，再考虑多 Agent

只有满足以下条件之一才增加子 Agent：

- 子任务需要独立且大量的上下文。
- 多个子任务可以并行进行。
- 专业角色之间有清晰输入输出边界。

如果一个普通函数或单 Agent 能可靠解决，不要为了展示而拆成多 Agent。

### 8. 权限规则不能替代沙箱

`allowed_tools`、Hook 和审批只能控制已知路径，不能提供操作系统级隔离。执行 Shell、处理不可信内容或服务多个用户时，应使用容器、微虚拟机或第三方沙箱，并限制网络与凭证。

## 常见误区

| 误区 | 调整方式 |
| --- | --- |
| 收集大量课程但不编码 | 每天至少产生一次可运行结果 |
| 同时学习多个同类框架 | 按计划顺序学习，并写出职责差异 |
| 只看最终回答 | 同时记录检索、工具、步骤和测试证据 |
| 用 Demo 成功代替质量证明 | 建立固定评测集并保留 Baseline |
| 把 Agent 当确定性程序 | 增加重试、超时、最大步数和人工审批 |
| 密钥写入配置文件 | 只使用环境变量或密钥管理服务 |
| Agent 直接运行在个人主目录 | 使用专用练习目录和隔离环境 |

## 卡住时的处理顺序

1. 缩小到最小可复现案例。
2. 保存完整错误信息和输入。
3. 查当前版本的官方文档和迁移说明。
4. 检查模型是否支持所需工具或结构化输出。
5. 用普通函数验证问题是否来自 Agent 框架。
6. 超过两天仍未解决时，先记录限制并继续不依赖该功能的任务。

## 进入下一阶段的规则

满足以下条件才进入下一阶段：

- 本阶段每周核心成果均已提交。
- 所有示例有运行方式或测试命令。
- 至少记录一个失败案例和解决过程。
- 阶段出口条件全部满足，或明确记录无法完成的原因与替代方案。
- 没有把真实密钥、凭证或敏感数据提交到仓库。
